# ADR-0009 — Tool Surface Refactor

**Date:** 2026-04-01
**Status:** Draft → Ready for Implementation
**Supersedes:** Portions of ADR-0007 (tool names), ADR-0008 (observe/steer)

---

## 1. Problem Statement

Five interrelated issues have accumulated:

1. **Transfer relay ceremony.** Every file transfer requires 3 steps: `prepare_relay` → construct curl → execute. Push and pull have asymmetric curl syntax. Agents and the orchestrator consistently fumble this.

2. **Exec blocking.** `exec(command=)` runs raw SSH with a 20s hard timeout. When SSH hangs, the claude.ai UI freezes. The `block_timeout_exec=5` config for remote clients is dead code — never applied to inline mode.

3. **Task output confusion.** `tasks()` returns container-internal paths (`/root/.maestro/task_output/...`) that agents mistake for Cellar host paths. The documented `read_output` tool was never implemented.

4. **Ghost and zombie tools.** `read_output` and `transfer` are documented but don't exist. `observe`, `steer`, and `poll` were "removed" by ADR-0007/0008 but still have live `@mcp.tool()` registrations.

5. **Naming inconsistency.** Tool names don't convey their category. `exec` vs `service` vs `dispatch` vs `run` — no naming convention.

---

## 2. Design Decisions

### 2.1 Files never pass through MCP

Every MCP tool result enters the LLM context window as tokens. A 50 KB file costs ~15K tokens whether the LLM reads it or not. The HTTP relay exists precisely because it's **out-of-band**.

**Therefore:** `transfer_pull_file` and `transfer_push_file` orchestrate the transfer server-side and return a ready-to-run curl command with auth baked in. File bytes always flow through HTTP.

### 2.2 Everything through tmux

`exec(command=)` inline mode bypasses tmux, blocking the UI for up to 20s with no tracking.

**Therefore:** All execution goes through tmux with auto-promote. Commands that complete within `block_timeout` return inline. Commands that don't return a task_id immediately. Every command gets a ledger entry.

### 2.3 Observe and steer fold into other tools

Testing confirmed: `observe` returns empty unreliably. `steer` reports false success on dead processes. Interactive agent steering has no working use case (agent CLIs require TTY).

The useful capabilities fold cleanly:
- **observe** (watch progress) → `read_task_output(task_id, tail=50)`
- **steer C-c** (graceful abort) → `stop_task(task_id, graceful=True)`

### 2.4 Service merges into run_task

`exec` and `service` are the same operation with different timeout semantics. Unified as `run_task(persistent=True/False)`.

### 2.5 Consistent naming

Tools are named by **category + action**: `_file` for file ops, `_task` for lifecycle, `_agent` for orchestration.

## 4. Tool Specifications

### 4.1 read_file

Quick file peek. Content returns in MCP context (costs tokens).

```
read_file(host: str, path: str) → file content
```

- Limit: **16 KB**, 10s timeout
- For larger files: use `transfer_pull_file`

### 4.2 write_file

Quick file write. Content sent as tool parameter (costs tokens).

```
write_file(host: str, path: str, content: str) → confirmation
```

- Limit: **16 KB**, 10s timeout
- For larger files: use `transfer_push_file`

### 4.3 transfer_pull_file

Pull a file from a fleet host via the relay. **File content never enters MCP context.**

```
transfer_pull_file(host: str, remote_path: str) → JSON
```

**Internal flow:**
1. Resolve host, validate path
2. SCP file from host → staging area inside Maestro container
3. Generate single-use ephemeral token (auto-registered, short TTL)
4. Build curl command with token baked into Authorization header
5. Return curl + metadata

**Response:**
```json
{
  "status": "staged",
  "host": "apollyon",
  "remote_path": "/home/rmstxrx/.../relay.py",
  "bytes": 15089,
  "filename": "relay.py",
  "curl": "curl -s -o relay.py -H 'Authorization: Bearer <token>' 'https://maestro.rmstxrx.dev/transfer/pull?host=_staged_&remote_path=/tmp/maestro/staged/<id>_relay.py'"
}
```

**Caller usage:**
```
# Step 1: tool call
transfer_pull_file(host="apollyon", remote_path="/home/rmstxrx/.../relay.py")

# Step 2: run the curl in bash_tool (copy-paste from response)
curl -s -o /home/claude/relay.py -H 'Authorization: ...' '...'
```

Two steps, zero thinking. Auth baked in. Works for any size up to 100 MB (relay config limit). Text and binary identical.

**Staging note:** Pulled files transit through `/tmp/maestro/staged/` inside the Maestro container — ephemeral storage, cleaned up after download or after a short TTL. Transfer files never persist on Cellar's ZFS pool. Only task output and the ledger persist (via the `/root/.maestro/` → `/volume2/docker/maestro/state/` Docker volume mount).

### 4.4 transfer_push_file

Push a file to a fleet host via the relay. **File content never enters MCP context.**

```
transfer_push_file(host: str, remote_path: str) → JSON
```

**Internal flow:**
1. Resolve host, validate path
2. Generate single-use ephemeral token
3. Build curl command with token and destination baked in
4. Return curl. Actual upload happens when caller runs it.

**Response:**
```json
{
  "status": "ready",
  "host": "eden-wsl",
  "remote_path": "/home/rmstxrx/.../config.yaml",
  "curl": "curl -s -F 'file=@<LOCAL_FILE>' -H 'Authorization: Bearer <token>' 'https://maestro.rmstxrx.dev/transfer/push?host=eden-wsl&remote_path=...'"
}
```

**Caller usage:**
```
# Step 1: tool call
transfer_push_file(host="apollyon", remote_path="/home/rmstxrx/.../config.yaml")

# Step 2: fill in local path, run in bash_tool
curl -s -F 'file=@/home/claude/config.yaml' -H 'Authorization: ...' '...'
```

### 4.5 run_task

Execute a command on a fleet host. Unifies former `exec` and `service`.

```
run_task(
    host: str,
    command: str = "",
    task_id: str = "",         # staged mode (pre-staged inbox script)
    cwd: str | None = None,
    expected_runtime: int | None = None,
    sudo: bool = False,
    persistent: bool = False,  # True = service mode (no ceiling)
    capture: bool = False,     # tee output to disk
    label: str = "",           # human-readable label
) → JSON
```

**Two modes by command source:**
- `command=` — tool stages the command internally, runs in tmux
- `task_id=` — runs a pre-staged script from `/tmp/maestro/inbox/`

**Two modes by lifetime:**
- `persistent=False` (default) — ceiling at 300s, auto-promotes after `block_timeout` (5s for remote clients). Normal task.
- `persistent=True` — no ceiling, always returns immediately with task_id. Runs until `stop_task`. For services, training runs, servers.

**What changed from `exec`:**
- `command=` path now goes through tmux + auto-promote (no more raw SSH blocking)
- `block_timeout_exec` from client profiles is now active
- Every command gets a ledger entry and is trackable via `current_tasks` / `read_task_output`
- `_INLINE_EXEC_MAX_TIMEOUT` and the raw SSH inline path are removed

**What changed from `service`:**
- Absorbed into `run_task(persistent=True)`
- `capture` and `label` parameters carry over unchanged

### 4.6 stop_task

Kill a running task.

```
stop_task(
    task_id: str,
    graceful: bool = False,   # True = send SIGINT first, wait, then kill
) → JSON
```

- `graceful=False` (default) — kills tmux window immediately (same as old `stop`)
- `graceful=True` — sends SIGINT (C-c) to the process, waits briefly for clean exit, then kills the window if still running. Replaces `steer C-c`.

Updates ledger with `status='killed'`.

### 4.7 current_tasks

Query the task ledger.

```
current_tasks(
    status: str | None = None,    # running|done|failed|timeout|orphaned|killed
    agent: str | None = None,     # codex|claude|gemini|exec
    host: str | None = None,
    task_type: str | None = None, # run|dispatch|service
    last: int = 10,
) → JSON
```

**Output format change — no more container paths:**

Before:
```json
{"task_id": "abc", "output_file": "/root/.maestro/task_output/abc.txt", "result_url": "..."}
```

After:
```json
{"task_id": "abc", "output_available": true, "output_hint": "Use read_task_output('abc') to read"}
```

### 4.8 read_task_output

Read captured output of a task by ID. Replaces the ghost `read_output` and folds in `observe` functionality.

```
read_task_output(
    task_id: str,
    tail: int | None = None,   # last N lines
    head: int | None = None,   # first N lines
    full: bool = False,        # True = return curl command for full file download
) → JSON
```

**Response (default, no head/tail/full):**
```json
{
  "task_id": "abc",
  "status": "done",
  "bytes": 8432,
  "content_preview": "first ~2000 chars...",
  "truncated": true,
  "hint": "Use tail= or head= for targeted reads, or full=True to download the complete file."
}
```

**Response (with tail/head):**
```json
{
  "task_id": "abc",
  "status": "done",
  "lines_requested": 50,
  "content": "last 50 lines..."
}
```

**Response (full=True) — file never enters MCP context:**
```json
{
  "task_id": "abc",
  "status": "done",
  "bytes": 84320,
  "curl": "curl -s -o task_abc.txt -H 'Authorization: Bearer <token>' 'https://maestro.rmstxrx.dev/transfer/pull?host=_staged_&remote_path=/tmp/maestro/staged/<id>_task_abc.txt'"
}
```

The `full=True` path generates a single-use URL pointing at the output file inside the Maestro container, returns the curl — same pattern as `transfer_pull_file`. The caller never needs to know where the file lives or what "cellar" vs "Maestro container" means.

**Response (task still running):**
```json
{
  "task_id": "abc",
  "status": "running",
  "bytes_so_far": 3200,
  "content": "output captured so far (tail 50)..."
}
```

Resolves the container-internal path automatically. Caller never sees `/root/.maestro/...`.

### 4.9 dispatch_agent

Dispatch an AI agent. Unchanged from current `dispatch` except the name.

```
dispatch_agent(
    host: str,
    agent: str,               # codex | gemini | claude
    prompt: str,
    working_dir: str,
    expected_runtime: int | None = None,
    model: str = "",
    reasoning_effort: str = "",
    approval_mode: str = "plan",
    context_files: list[str] | None = None,
    resume: str = "",
    allowed_tools: str = "",
) → JSON
```

Always returns `{task_id}` immediately (background). Monitor with `current_tasks`, read with `read_task_output`.

### 4.10 orchestra_status

Fleet health check with auto-reconnect and optional agent discovery.

```
orchestra_status(
    host: str = "",       # specific host, or "" for all
    agents: bool = False, # also check agent CLI availability
) → JSON
```

Unchanged from current `status` except the name.

### 4.11 prepare_relay

Get an ephemeral bearer token. Rarely needed — `transfer_pull_file` and `transfer_push_file` handle auth automatically.

```
prepare_relay() → JSON {"value": "<token>", "ttl_seconds": 3600}
```

Only needed for: direct `/tasks/{id}/result` HTTP polling, custom workflows, or edge cases not covered by the transfer tools.

## 5. Decision Trees

### Reading a file from a fleet host

```
Need to peek at contents and reason about them inline?
  ≤ 16 KB  → read_file(host, path)
  > 16 KB  → transfer_pull_file(host, path) → run curl → view locally

Need the file in this sandbox (to edit, push elsewhere)?
  Any size → transfer_pull_file(host, path) → run curl
```

### Writing a file to a fleet host

```
Small inline content already in context?
  ≤ 16 KB  → write_file(host, path, content)

Larger, or file on disk in this sandbox?
  Any size → transfer_push_file(host, path) → fill in local path → run curl
```

### Getting task output

```
Is it done?
  → current_tasks(status="running")

Quick look?
  → read_task_output(task_id)
  → read_task_output(task_id, tail=50)

Full output file into this sandbox?
  → read_task_output(task_id, full=True)
    Returns a curl command (same pattern as transfer_pull_file).
    No host names, no container paths — just the task ID.
```

### Running things

```
Quick command (git status, ls, cat)?
  → run_task(host, command="git status")
    Returns inline if <5s, else {task_id}

Long script already staged?
  → run_task(host, task_id="abc123")

Long-running service (vLLM, Jupyter)?
  → run_task(host, command="...", persistent=True, capture=True, label="vllm")

Dispatch an AI agent?
  → dispatch_agent(host, agent="codex", prompt="...", working_dir="...")
```

## 8. Summary

**14 → 11 tools.** Every name says what it does. Categories group naturally.

| Category | Tools | Count |
|----------|-------|-------|
| File I/O | `read_file`, `write_file`, `transfer_pull_file`, `transfer_push_file` | 4 |
| Task Lifecycle | `run_task`, `stop_task`, `current_tasks`, `read_task_output` | 4 |
| Orchestration | `dispatch_agent`, `orchestra_status` | 2 |
| Infrastructure | `prepare_relay` | 1 |
| **Total** | | **11** |

**Key wins:**
- Transfer: 2 steps (tool → curl) instead of 3 (prepare_relay → construct curl → run). Auth baked in. Files never in context.
- Execution: no more 20s UI freezes. Everything tracked. `block_timeout` works.
- Output: one tool, one ID. No container paths. No output retrieval maze.
- Naming: `_file`, `_task`, `_agent` — self-documenting categories.
- No ghosts, no zombies, no dead config.
